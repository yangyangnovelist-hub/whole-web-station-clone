# ETH、SOL、XRP、DOGE 5m 上的 G/H：币安跳变后吃 Polymarket 的旧卖一（设计，2026-10-04 写死，跑之前提交）

## 为什么

BTC 5m 上的 G/H 在 GitHub 前向录制的毫秒盘口上（2026-10-01 02:30 UTC 起，`real/forward-latency-curve.md`，forward_variants.py 算）每份：

| 延迟 | G 首笔 | H 反向 2 倍 |
|---|---:|---:|
| 0.3 秒 | +10.4¢ | +12.1¢ |
| 0.4 秒 | +6.0¢ | +7.3¢ |
| 0.5 秒 | +3.7¢ | +5.0¢ |

前向录制（ci/forward.json）一直同时录 ETH、SOL、XRP、DOGE 的 5m 盘口和各自的币安 USDT 逐笔成交，但从没用 G/H 看过（检验 C 9/30 09:40 改成只用 BTC，F、G、I、J 都只用 BTC）。如果其他四个币种也成立，交易次数能翻几倍。这里不改规则、不挑参数，把 BTC 上的同一代码路径原样放到四个币种上：先做一次描述性的独立检验，再对结果为正的币种写死一个前向检验。

先验并不乐观：5 月–8 月的稠密数据上，同一个公平价筛选规则（θ = 12¢，300 ms）在 ETH 上 A/B/C 三段是 −0.01¢ / +5.23¢ / −2.95¢，SOL 是 −0.86¢ / −3.08¢（`real/cross-gated-eth.md`、`real/cross-gated-sol.md`），ETH 的过期报价 300 ms 内就没了、卖一挂单量只有 BTC 的四分之一（`real/cross-stale-eth.md`）。十月的 GitHub 盘口是另一段行情，所以还是要看。

## 数据

- GitHub 前向录制（polymarket-forward 通道）每段录制的 `bundle-<coin>/latency/`（recording.LatencyFiles）：该币 5m 市场的 Up 盘口（每条消息带 Polymarket 自己的时间戳）、官方结果、币安 `<COIN>USDT` 逐笔成交（data-stream.binance.vision，带交易所时间，`binance_trades.jsonl.gz`），和 CLOB 断线时刻（`clob_closes.csv.gz`）。
- 在 polymarket-late-ms 通道上跑（它下载所有前向录制；解包的 `bundle-*/latency` 已经覆盖五个币种，已核对）。脚本 `alts.py`，报告 `real/alts.md`，判定 `real/alts.verdict.md`，判定用的成交 `real/alts.trades.csv`。

## 规则（原样沿用 BTC 的代码和参数，币种作为参数显式传入）

都用 `latency.gated_trades`，参数取自检验 G（`G_SPOT`、`G_Z0` = 2、`G_THETA` = 12¢、`G_TAU_LO` = 15、`G_MAX_PRE` = 3¢），每段录制单独算（`latency._per_recording`），和 forward_variants.py 算 BTC 曲线的调用完全相同，只是币种换掉：

- 候选：该币自己的币安逐笔成交，剩 240–15 秒，对数价相对 1–5 秒前最后一笔涨跌超过 2σ（σ 是该币自己 1 秒收益的 10 分钟滚动标准差，到前一整秒为止，不跨过 10 秒以上的空档）。
- **G 首笔**：以触发时交易所显示的 Up 中间价为原来的概率，加上这次涨跌对结算 TWAP 的影响得到公平价；触发前 2 秒内 Up 中间价已经朝要买的方向动了 ≥ 3¢（或 2 秒前没有报价）就跳过；L 秒后按卖一买顺势一方，公平价 − 卖一 − 手续费 ≥ 12¢ 才买；每个市场只取第一笔。
- **H 反向 2 倍**：公平价从触发前 2 秒的 Up 中间价起算，加上这 2 秒币安的涨跌；不跳过；同一市场每次都买，买到后 2 秒内不再买；第一笔和与第一笔同方向的加仓每笔 1 份，反方向的加仓每笔 2 份（`latency.opp_weights`）。
- 执行和费用（两条规则相同，和 BTC 相同）：L = 从币安成交的交易所时间到我们的单按卖一成交，含 Polymarket 的 150 ms 吃单冻结；按那一刻交易所时间戳盘口的卖一（Down 的卖一 = 1 − Up 买一），0.02–0.98；taker 费 0.07·p(1 − p)；持有到官方结算。盘口要在跑（成交时刻前 30 秒、后 10 秒内有更新），触发到成交之间 CLOB 不能断线；同一市场在两段录制里出现时取最早的。
- 延迟 L：0.2、0.25、0.3、0.35、0.4、0.45、0.5 秒。

## 一、独立的描述性检验（只报告，不判定）

- 市场：2026-10-01 02:30 UTC（检验 G 和 BTC 曲线的起点）起、2026-10-04 21:30 UTC 之前开始的 ETH、SOL、XRP、DOGE 5m 市场，已有的全部前向录制。BTC 同一段、同一代码一起列出作对照（应与 forward-latency-curve.md 同段的数一致）。
- 每格：每份赚的钱（H 是 Σ份数×盈亏 / Σ份数）± 按市场聚类的标准误、笔数、单边正态 p（`latency.clustered`）。
- 频率和钱：有盘口的市场数；录到的天数 = 有盘口的市场数 × 300 秒 / 86,400 秒（录制只覆盖每天的一部分，按“录满一整天”折算）；每天有成交的市场数、每天笔数；每天美元：每笔 5 份（H 反向加仓 10 份），和每笔 min(20, 卖一挂单量) 份（H 反向加仓 min(40, 挂单量)）。
- 对照（每条规则、每个延迟、每个币种，同样份数）：
  - 反方向：同一笔成交的同一时刻（触发后 L 秒）买另一边的卖一（0.02–0.98，不设门槛）。
  - 随机时刻、随机方向：每笔成交配一个同一市场剩 240–15 秒内均匀的随机时刻和随机方向，L 秒后按卖一买（同样的盘口在跑、断线检查和 0.02–0.98）；随机数按币种、规则和触发时刻（毫秒）各自取。
- 前后两半：按市场开始时间把每个币种的市场分成两半，各报 0.4 秒的两条规则。

## 二、前向检验（写死）

**150 ms 吃单冻结**：2026-10-04 20:35 UTC 查 CLOB `/clob-markets/{condition_id}`，五个币种当时的 5m 市场（开始于 2026-10-04 20:30 UTC）都是 `itode: true`，和 BTC 5m 一样有 150 ms 吃单冻结；费率 `fd.r` = 0.07，最小 5 份；tick：BTC、SOL、DOGE 0.01，ETH、XRP 0.001。所以 BTC 上“0.4 秒约是实盘服务器加 150 ms 冻结能做到的延迟”对四个币种同样适用。`alts.py --itode` 每次运行再查一遍写进报告；就算以后某个币种不再是 itode，规则和延迟也不改，只在报告里注明。

**入选**：ETH、SOL、XRP、DOGE 中，独立段上 G 首笔 0.4 秒每份 > 0 的币种进入前向。入选在本文件提交后 polymarket-late-ms 通道第一次成功运行 `alts.py` 时，按当时已下载的独立段数据（只用 21:30 之前开始的市场）自动定下，写入 `real/alts.verdict.md`，之后不再改。BTC 不在其中（它有自己的检验 G、I、J）。

**规则**：G 首笔，0.4 秒，参数同上。

**市场**：2026-10-04 21:30 UTC 及以后开始的市场（在本文件提交之后）。

**判定**：每个入选币种分别判定一次：前向段按触发时间攒满 600 笔后，取前 600 笔，同时满足以下三条才算通过：
1. 每份 > 0；
2. 按市场聚类的单边正态 p < 0.025 / 4 = 0.00625（4 = 四个币种，不管几个入选都按 4 算）；
3. 前 300 笔和后 300 笔每份都为正。

判定一行写入 `real/alts.verdict.md`（只追加，写过的行只读回、不重算，同 rt_fwd.py），这 600 笔追加到 `real/alts.trades.csv`。不到 600 笔不判定；前向录制停止（ci/forward.json 的 until 是 2026-10-27）时还不到 600 笔就没有判定。没入选的币种前向段只描述，不判定。

## 实现补充（2026-10-04 约 20:50 UTC，提交 alts.py 时写，仍在任何运行之前）

- “成功运行”按币种算：这次运行里该币种在独立段至少有一笔 G 首笔 0.4 秒成交，才定它的入选；一笔都没有（比如录制没解出来）就不定，等下一次。
- 对照只跟着留下的成交（同一市场在两段录制里时，G 首笔取最早那笔，它的对照也取那一段的）。H 的胜率、均价按份数加权。
- 报告里 BTC 一列是同一代码、同一段市场的对照，不入选、不判定。
