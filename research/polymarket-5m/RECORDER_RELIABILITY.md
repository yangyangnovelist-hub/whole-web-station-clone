# 录制链路修复与验收

## 已确认的问题

核查源分支提交 `573e44f3f1ba2bad054375d5ec8732879fb79f2b`。

GitHub forward run `38869686142` 的采集步骤在 2026-10-16 13:40:44 UTC 结束，后续诊断、等待结果、转换、研究和上传仍占用整个工作流的 concurrency 锁。下一次 run `38909708508` 虽在 13:40:46 被派发，但采集步骤直到 15:37:20 才开始。两次采集步骤间隔 1 小时 56 分 36 秒；工作流显示运行不等于 websocket 一直在录制。

上一轮日志也包含 `slow consumer: send buffer full`。旧 Recorder 在接收事件循环里同步 JSON 编码、gzip 压缩和文件写入。该实现存在处理跟不上输入的风险；不能仅凭错误文本断言压缩是唯一瓶颈，也不能将所有连接 epoch 都解释成网络故障。

这些证据仅对应 GitHub 采集链，不证明另一个本地或云端常驻录制器没有采集。已存但未接入回放、缺少字段、尚未结算、无流动性与实际断流必须分开。

## 本次修改

1. 工作流拆成 `record` 与 `analyze`。采集与原始快照交接使用原有锁；研究使用另一把锁。转换、结算等待、研究超时不再堵住后续采集。当前已经运行的旧任务不会被取消。
2. 先保存完整原始消息交接包和 SHA256，再开始转换；分析任务恢复时复核归档和每个文件的校验值。复制范围不包含 `.env` 或环境变量。原始交接包只保留 1 天以限制临时存储，既有转换工件继续保留 30 天；它不是永久原始数据仓库。
3. `record_live_buffered.py` 复用未改动的 paper_trader 网络与决策代码，仅替换写入器并加监督。gzip/文件 I/O 在单独线程，JSON 在调用时固化；不改本地接收时间，不把实际写入时间冒充接收时间。64 MiB 字节队列和 65,536 条队列均有上限，过载或磁盘错误明确失败，不静默丢弃。
4. 每约 10 秒记录进程、CLOB 连接状态、事件循环延迟、排队字节、写入/flush 数和各流最新入队时间。心跳和 gzip flush 均不能冒充全流完整性或断电持久性证明。监督发现写入失败会取消采集并保留失败元数据。
5. 后续派发有重试；连续三次采集或交接失败停止链并显式报错，避免故障下无限启动。日期/启停/币种配置保留不变，当前 `until` 仍为 2026-10-27。

## 尚不能声称的结果

这不是已经完成一次 24 小时生产实测。GitHub runner 排队、依赖启动、打包/上传仍可能造成交接间隙。修复后须从新运行的真实接收时间和心跳验收实际改善，不能用离线测试或任务绿灯证明全天零丢失。
