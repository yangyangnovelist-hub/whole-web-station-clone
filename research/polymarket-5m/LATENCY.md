# 延迟：目标、预算、改什么、怎么监控

回测里的“延迟”是：**币安成交的交易所时间 → 我们的单在 Polymarket 按当时的卖一成交**，里面包括 Polymarket 对吃单的 150 ms 冻结（9 月 4 日起，冻结期间不能撤单）。

## 为什么是头号问题

GitHub 前向录制的盘口（10/1 03:00 → 10/2 05:05 UTC，每份 ± 按市场聚类的标准误）：

| | 0.3 秒 | 0.4 秒 |
|---|---:|---:|
| G 首笔 | +6.4¢（74 笔） | +0.3¢（57） |
| H 每次都加 | +8.7¢（137） | +2.8¢（112） |
| H 反向 2 倍（检验 I 的规则） | +10.3¢ ±3.6 | +6.4¢ ±4.4 |

从 0.3 秒到 0.4 秒，100 ms 就把首笔的优势吃光了。每 50 ms 一格的曲线（10/2 08:38 UTC 第一次算出来，[`real/forward-latency-curve.md`](real/forward-latency-curve.md) 每轮录盘后自动更新）：

| 延迟 | G 首笔 | H 每次都加 | H 反向 2 倍 |
|---|---:|---:|---:|
| 0.20 秒 | +13.3¢（103） | +12.8¢（210） | +15.3¢ |
| 0.25 秒 | +13.6¢（94） | +13.2¢（174） | +14.1¢ |
| 0.30 秒 | +6.4¢（74） | +8.7¢（137） | +10.3¢ |
| 0.35 秒 | +4.9¢（64） | +5.8¢（114） | +7.8¢ |
| 0.40 秒 | +0.3¢（57） | +2.8¢（112） | +6.3¢ |
| 0.45 秒 | −4.3¢（54） | −1.0¢（110） | +3.1¢ |
| 0.50 秒 | −6.8¢（53） | −1.2¢（110） | +3.5¢ |

0.25 → 0.30 秒是一道坎（正好是别的抢单程序成交放量的时候，见下）：压到 0.25 秒，每份约翻倍，笔数多三到五成。首笔在 0.40 秒左右归零，所以延迟闸门先定在 0.40 秒。标准误 3–6¢，样本还小，曲线会随录盘更新。

**对手什么时候到**（用户本地，3 天 8,853 次币安跳变）：顺着跳变方向的吃单成交，在 +200 ms 以前只是平时的 1.0–2.1 倍，+250–300 ms 放大到 4.5 倍，+300–350 ms 到 7.2 倍。成交时间已经包括 150 ms 冻结，所以别的抢单程序在跳变后约 100–200 ms 把单送到 Polymarket，最快的已经接近东京到伦敦的物理下限。我们在 0.3 秒成交，正好落在这一波中间；到 0.4 秒，便宜的卖一大多已被抢走或撤掉。

## 0.3 秒的预算

| 段 | 物理下限 | 目标 | 怎么量 |
|---|---:|---:|---|
| 币安撮合 → 推送出来 | 几 ms | ≤ 10 ms | `feeds.py`（交易所时间戳 → 本机，要先对时） |
| 东京 → 欧洲 | 约 100 ms | ≤ 115 ms | 同上 |
| 本机：收到 → 订单发出 | < 1 ms | ≤ 5 ms | 引擎打点（见下） |
| 都柏林 → Polymarket（伦敦 AWS eu-west-2）+ 网关 | 约 5 ms | ≤ 15 ms | `feeds.py` 的 `/time` 往返；真实订单的回执时间 |
| 吃单冻结 | 150 ms | 150 ms | 固定 |
| **合计** | **约 260 ms** | **≤ 300 ms** | |

物理下限之外只有约 40 ms 的余量，所以每一段都要压，而且要砍掉慢的尾巴。

## 已知的浪费

9 月都柏林导出的数据里，引擎在币安成交后**中位 0.27 秒**才收到（`BINANCE_AGG_TRADE`），而东京到欧洲的物理下限约 0.1 秒，中间约 170 ms 没解释。当时的三个嫌疑（10/2 已查清：主要是第 1 条，见下一节）：

1. **永续 `aggTrade` 每 100 ms 才推一批**（[币安文档](https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-market-streams/Aggregate-Trade-Streams)）。平均晚 50 ms，最多晚 100 ms。现货 `@trade`、`@bookTicker` 和永续 `@bookTicker` 都是实时的。回测用的是现货逐笔。
2. **时钟没对准**：收到时间用的是本机的钟，成交时间用的是币安的钟。没开 chrony 时，两者能差几十到几百毫秒。
3. **引擎排队**：同一个 Python 事件循环里还要处理 Polymarket 盘口（快速行情时每秒几百条）、写库和打日志，急动时消息会排队。

## 改动清单和实测结果（用户本地，2026-10-02）

| 条目 | 结果 | 结论 |
|---|---|---|
| 1. 换信号源 | 新链路早已用现货逐笔。9 月引擎用的永续聚合流在币安那边就晚约 150 ms，“170 ms 没解释”主要是它，已经省掉。**现货最优价推送（`@bookTicker`）比成交推送更早反映跳变**：1bp 跳变中位早 21 ms，2bp 早 39 ms；最优价看到的跳变 98–100% 随后都有同向成交，不是假信号。永续不领先。 | 触发改成“最优价和成交谁先到用谁”，省 14–40 ms |
| 多连接取最先到 | 4 条连接：中位 109.0 → 105.7 ms，99% 213 → 180 ms | 平均只省 4 ms，主要砍尾巴；值得开 |
| 2. 对时 | 都柏林等机器已经接 AWS 授时，误差微秒级 | 不用改 |
| 3. 热路径 | 试点代码 1–2 ms，连接保持热着，打点基本齐全 | 还缺：真实撮合时刻、90% 超 0.35 秒报警、没有热连接时不发单 |
| 4. ~~搬伦敦~~ | **不行**：Polymarket 的地区限制里，英国在网页和接口上都只能平仓、不能开新单；爱尔兰只限制网页，接口不受限（[Polymarket 文档](https://docs.polymarket.com/developers/CLOB/geoblock)） | 留在都柏林 |
| 5. ~~东京中继~~ | 直连都柏林中位 105 ms，经东京转发 151 ms，7.3 万笔里转发从没先到过 | 不用；直连已贴着物理下限 |
| 6. 延迟闸门 | 交易所那段延迟事先预测不了：相邻两张单的延迟几乎不相关 | 只能按发单前看得到的东西设闸：触发已过去多久、有没有热连接 |

**两条延迟曲线互相印证。** 本地在都柏林 9/29–10/1 的盘口上，G 只吃卖一 0.35 秒每份 +3.8¢、0.40 秒 +0.6¢，坎在 0.35–0.40 秒；GitHub 盘口上坎在 0.25–0.30 秒。差的 50–100 ms 正好是都柏林录制机晚的那部分。所以按真实时间算，目标仍是**币安跳变到撮合 ≤ 0.25–0.30 秒**。

**交易所那段 140 ms 在撮合前还是撮合后，决定 G/H 能不能做。** 9 月实盘下单往返中位 349 ms。扣掉网络约 10 ms 和 150 ms 冻结，剩约 165 ms。本地看了 9 月客户端的代码：用的是官方客户端（HTTP/2、长连接，一单一个请求），唯一的额外开销是连接空闲 30 秒过期后重新握手，约 20–25 ms，新链路每 15 秒保活一次，已经消除。剩下约 140 ms 在交易所那边：

- 在撮合**之后**才回执：对撮合时刻无害，币安跳变 → 撮合 ≈ 105（币安到都柏林）+ 5（到伦敦）+ 150 ≈ **0.26 秒**，在曲线上明显赚钱的一段；
- 在撮合**之前**处理（验签、查余额等）：推迟撮合，我们压不掉，≈ **0.40 秒**，优势基本为零。

市场上最快的吃单在跳变后 +250 ms 就成交，偏向前一种，但只有真单能确认（见最后一节）。

## 每次触发要记的时间

全部用对过时的本机时钟，毫秒：

- 币安成交时间；
- 收到时间；
- 算完的时间；
- 订单发出的时间；
- HTTP 回执的时间；
- 成交结果；
- 当时 Polymarket 盘口最后一次更新的交易所时间。

每天统计各段的 p50 / p90 / p99。**合计的 p90 超过 0.35 秒就报警。**

## 录制机本身也要体检

回测和实盘监控都靠录下来的盘口；录制机晚多少，回测就虚高多少。到目前为止的排序：

- GitHub 前向录制：最可靠，基准；
- 都柏林：比 GitHub 晚约 50–100 ms，偏乐观；
- 香港：晚 0.25–0.5 秒，不能用于 G/H。

`recorder_check.py` 量三样：

- 币安急动后 +0.1…+2 秒显示了 Polymarket 最终反应的多少；
- 中间价第一次朝急动方向动 1¢ 要多久；
- 收到时间 − 交易所时间。

GitHub 录制每轮自动量一次，写在 [`real/recorder-check.md`](real/recorder-check.md)。新的录制机先用同一段时间、同一批币安成交量一遍，和 GitHub 对上了再信它的回测。

## 不花钱怎么验证

- `feeds.py`（都柏林，10/3 06:06 UTC 结束）：
  - 各源从交易所到本机的 p50 / p90 / p99；
  - 2σ 急动哪个源最先到、别的晚多少；
  - Polymarket `/time` 往返。
- `real/forward-latency-curve.md`：每压 50 ms 值多少钱、闸门放在哪。
- 只有真实订单能量到 Polymarket 网关处理订单要多久（`/time` 量不到这一段）。

## 零风险测交易所那一段（不成交、不付手续费；写死于 2026-10-04）

真单试点（10 张 FAK）：发单 → 回执中位 310 ms，唯一一笔成交发单 → 撮合 375 ms，比 150 ms 冻结加 5 ms 网络多出约 150–220 ms。可是盘口上最快的吃单在币安跳变后 +250 ms 就成交，说明他们几乎没有这一段。要先分清多出来的时间花在哪：

1. **只挂单（post-only）发单 → 回执**：BTC 5m 当前市场，买 5 份，价格 0.01（远离市价，不会成交，占用保证金 $0.05），收到回执后立刻撤单。同时记 撤单 → 回执。平静时刻 20 次、币安 2σ 急动后 20 次（用同一条触发链路）。
2. **同样的单在 `/time` 往返旁边对照**：每次发单前后各量一次 `/time`。
3. **判读**：
   - 只挂单回执 ≈ `/time` 往返（10–20 ms）→ 网关和验签不慢，多出的时间在吃单路径（冻结后的第二次校验或撮合排队）。再看急动时刻是否明显变慢：变慢 → 排队；不变 → 冻结后的固定开销。
   - 只挂单回执也有 150 ms 以上 → 网关或验签慢。下一步换普通钱包签名（签名类型 0）对比现在的代理钱包。
   - 撤单回执 ≤ 30 ms → 挂单方向（做市，或按信号只挂一边）可以靠币安触发的撤单躲开抢单：快的吃单最早在跳变后约 +250 ms 成交，我们的撤单约 +110 ms 就能到。
4. 每张单只挂几十毫秒、价格离市价很远，不会成交，不付手续费；要用账户签名，由用户或本地会话执行。

## 用真单量撮合时间（要动真钱，开不开由用户决定）

方案在动钱之前写死（2026-10-02），只为量延迟，不为赚钱：

- **下单**：只在新链路真实的 G/H 信号上下单，触发用“最优价和成交谁先到”。BTC 5m，买信号那一边，每张 5 份（最小量），卖一在 0.15–0.60 之间才下（每张不超过 $3）。限价 = 卖一 + 3¢（不超过 0.95）的 FAK，保证成交、拿到撮合时间。同时最多 2 张没结算的仓位。下满 10 张，或账户余额 < $1.5 就停。
- **每张记**：触发事件的币安交易所时间、本机收到时间、发单时间（写入连接前那一刻）、HTTP 回执时间、订单号、状态、成交价和份数；以及这笔成交的交易所撮合时间（用户频道的成交消息，或市场频道里对上价格、份数和时间的那笔 `last_trade_price`）。
- **对时**：取同一时段 Polymarket 盘口消息“收到 − 交易所时间”的最小值，当作两边时钟差加单程网络（约 5 ms）的上限，用来校准“撮合 − 发单”。
- **判定**（看中位数）：
  - 撮合 − 发单 ≤ 175 ms：那 140 ms 在撮合之后，对我们无害。再看币安 → 撮合：≤ 0.28 秒，就值得进入下一步（加大量的实盘检验，仍由用户决定）。
  - 撮合 − 发单 ≥ 270 ms：那 140 ms 在撮合之前，币安 → 撮合约 0.40 秒，现在的链路做不了 G/H，停。
  - 介于两者之间：再下 10 张（要充值）。
- 10 张的盈亏不作任何判断。

引擎的改动要由你或本地会话来做，云端不碰实盘程序、服务器和钱包。
