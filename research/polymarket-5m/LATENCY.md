# 延迟：目标、预算、改什么、怎么监控

回测里的“延迟”是：**币安成交的交易所时间 → 我们的单在 Polymarket 按当时的卖一成交**，里面包括 Polymarket 对吃单的 150 ms 冻结（9 月 4 日起，冻结期间不能撤单）。

## 为什么是头号问题

GitHub 前向录制的盘口（10/1 03:00 → 10/2 05:05 UTC，每份 ± 按市场聚类的标准误）：

| | 0.3 秒 | 0.4 秒 |
|---|---:|---:|
| G 首笔 | +6.4¢（74 笔） | +0.3¢（57） |
| H 每次都加 | +8.7¢（137） | +2.8¢（112） |
| H 反向 2 倍（检验 I 的规则） | +10.3¢ ±3.6 | +6.4¢ ±4.4 |

从 0.3 秒到 0.4 秒，100 ms 就把首笔的优势吃光了。更细的曲线（0.20–0.50 秒，每 50 ms 一格）在 [`real/forward-latency-curve.md`](real/forward-latency-curve.md)，每轮录盘后自动更新。

**对手什么时候到**（用户本地，3 天 8,853 次币安跳变）：顺着跳变方向的吃单成交，在 +200 ms 以前只是平时的 1.0–2.1 倍，+250–300 ms 放大到 4.5 倍，+300–350 ms 到 7.2 倍。成交时间已经包括 150 ms 冻结，所以别的抢单程序在跳变后约 100–200 ms 把单送到 Polymarket，最快的已经接近东京到伦敦的物理下限。我们在 0.3 秒成交，正好落在这一波中间；到 0.4 秒，便宜的卖一大多已被抢走或撤掉。

## 0.3 秒的预算

| 段 | 物理下限 | 目标 | 怎么量 |
|---|---:|---:|---|
| 币安撮合 → 推送出来 | 几 ms | ≤ 10 ms | `feeds.py`（交易所时间戳 → 本机，要先对时） |
| 东京 → 欧洲 | 约 100 ms | ≤ 115 ms | 同上 |
| 本机：收到 → 订单发出 | < 1 ms | ≤ 5 ms | 引擎打点（见下） |
| 欧洲 → Polymarket（伦敦 AWS eu-west-2）+ 网关 | 伦敦约 1 ms，都柏林约 5 ms | ≤ 15 ms | `feeds.py` 的 `/time` 往返；真实订单的回执时间 |
| 吃单冻结 | 150 ms | 150 ms | 固定 |
| **合计** | **约 260 ms** | **≤ 300 ms** | |

物理下限之外只有约 40 ms 的余量，所以每一段都要压，而且要砍掉慢的尾巴。

## 已知的浪费

9 月都柏林导出的数据里，引擎在币安成交后**中位 0.27 秒**才收到（`BINANCE_AGG_TRADE`），而东京到欧洲的物理下限约 0.1 秒，中间约 170 ms 没解释。三个嫌疑，明天 `feeds.py` 的结果能分开：

1. **永续 `aggTrade` 每 100 ms 才推一批**（[币安文档](https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-market-streams/Aggregate-Trade-Streams)）。平均晚 50 ms，最多晚 100 ms。现货 `@trade`、`@bookTicker` 和永续 `@bookTicker` 都是实时的。回测用的是现货逐笔。
2. **时钟没对准**：收到时间用的是本机的钟，成交时间用的是币安的钟。没开 chrony 时，两者能差几十到几百毫秒。
3. **引擎排队**：同一个 Python 事件循环里还要处理 Polymarket 盘口（快速行情时每秒几百条）、写库和打日志，急动时消息会排队。

## 改动清单（按能省的毫秒排序）

1. **换信号源。** 用币安现货 `btcusdt@trade` 加永续 `btcusdt@bookTicker`，不再用永续 `aggTrade`。平均省约 50 ms，尾巴省 100 ms。同一个流开 2–3 条连接，按成交编号去重，用最先到的那条，砍掉慢的尾巴。
2. **对时和打点。** 用 chrony 接 AWS Time Sync（169.254.169.123），误差 < 1 ms。不对时，其他改动都量不准。
3. **热路径单独跑。** 单独一个进程，只做“收币安 → 算公平价 → 发单”：
   - 盘口从内存里读最新值。
   - 不写库、不打同步日志；打点写进内存缓冲，再由另一个线程落盘。
   - 每个市场开盘时，把两边、一组价格和份数的订单预先签好，触发时挑一张直接发。签名不在热路径上。
   - 保持 2 条以上 HTTPS 长连接（keep-alive、TCP_NODELAY），每秒发一次 `/time` 保活。
   - 用 orjson 加 uvloop，或者用 Rust/Go 写。
   - 能省 5–50 ms，取决于现在的实现。
4. **服务器搬到伦敦 eu-west-2**，和 Polymarket 撮合在同一个区。用固定性能的实例（c7i/c7a 这类），不要 t3 这种突发型。约省 5 ms，路由更稳。
5. **东京中继（可选，先量再定）。** 在 ap-northeast-1 放一台小机器收币安，走 AWS 骨干网转发到伦敦。距离一样，但可能比公网稳。和直连 A/B 对比，尾巴短了才用。
6. **延迟闸门（保证一致性的关键）。** 每次触发时算：

   > 已用时间（现在 − 币安成交时间）+ 预计到达 Polymarket 的时间 + 150 ms

   超过阈值就不发。阈值取延迟曲线上优势归零的那一点（按 GitHub 现有数据大约 0.4 秒，曲线更新后再定）。慢的那部分直接放弃，而不是亏着钱去做；这样延迟偶尔变差时，少的只是笔数，每份的优势不变。

## 每次触发要记的时间

全部用对过时的本机时钟，毫秒：

- 币安成交时间；
- 收到时间；
- 算完的时间；
- 订单发出的时间；
- HTTP 回执的时间；
- 成交结果；
- 当时 Polymarket 盘口最后一次更新的交易所时间。

每天统计各段的 p50 / p90 / p99。**合计的 p90 超过 0.35 秒就报警。**

## 不花钱怎么验证

- `feeds.py`（都柏林，10/3 06:06 UTC 结束）：
  - 各源从交易所到本机的 p50 / p90 / p99；
  - 2σ 急动哪个源最先到、别的晚多少；
  - Polymarket `/time` 往返。
- `real/forward-latency-curve.md`：每压 50 ms 值多少钱、闸门放在哪。
- 只有真实订单能量到 Polymarket 网关处理订单要多久（`/time` 量不到这一段）。要不要小额试单是你的决定。

引擎的改动要由你或本地会话来做，云端不碰实盘程序、服务器和钱包。
